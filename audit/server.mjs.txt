PURPOSE
server.mjs is the central, monolithic Node.js HTTP server for the IsotopeAI self-hosted edition. It provides a comprehensive set of backend services including:
- Static file serving for the frontend application.
- Authentication and session management (JWT verification, session cookies).
- An integrated Admin Panel for database management, role assignment, and system health monitoring.
- A proxy layer for Supabase REST, Storage, and Edge Functions.
- Backup and restore orchestration using the BackupManager.
- AI proxying for Gemini, Groq, and YepAPI.
- Runtime patching of frontend JavaScript bundles to inject environment variables and modify application behavior.
- PWA support and service worker coordination.

ROLE IN THE APPLICATION
The file acts as the primary runtime glue. It eliminates the need for a complex build-step for environment configuration by patching assets on-the-fly. It handles all administrative tasks that require elevated permissions (Service Role Key) and provides a secure bridge between the client and the Supabase backend.

STATIC FILE SERVING ANALYSIS
The server uses `fs.readFileSync` and `path.join` for static assets under `/public`. It protects against traversal by normalizing paths and checking for known assets. It implements SPA fallback (serving index.html for unknown routes) and sets specific cache headers (IMMUTABLE for hashed assets, NO_STORE for sensitive/dynamic ones).

AUTHENTICATION ANALYSIS
The system uses a custom "username-auth" layer on top of Supabase. It maintains its own JWT verification logic and session cookie (`iso_admin` for admin panel). Admin auth can be satisfied by a static `ADMIN_SECRET` or a valid Supabase session from a whitelisted email.

BUNDLE PATCHING ANALYSIS
The server intercepts requests for specific JS assets and modifies their content:
- `getPatchedAIStoreBundle`: Injects API keys.
- `getPatchedAuthBundle`: Swaps email-auth for username-auth UI.
- `getPatchedAppBundle`: Forces 'ranker' plan and disables demo mode.
- `getPatchedInvitesBundle`: Fixes parameter name mismatches (`token_input` -> `p_code`).

SECURITY AND PRIVACY
- CSRF: POST routes lack traditional CSRF tokens but often rely on Bearer tokens or Admin Secrets.
- Admin Cookie: Signed with `ADMIN_COOKIE_SECRET` (HMAC SHA-256).
- Path Traversal: Risk is mitigated by strict path checks and restricted root.
- Injection: High risk in `/api/apply-sql` as it allows raw SQL execution.

FINDINGS
- SRV-001: [HIGH] Raw SQL Execution. The `/api/apply-sql` route allows potentially destructive operations if an admin account is compromised.
- SRV-002: [MEDIUM] Hardcoded Default Credentials. `DEFAULT_SUPABASE_ANON_KEY` is present in the source, though it's for a public/anon instance.
- SRV-003: [LOW] Large Monolith. The 8000+ line file is difficult to audit and maintain, increasing the risk of logic errors.
- SRV-004: [INFO] Bundle Patching Brittle. Patching depends on exact string matches in minified bundles, which will break on frontend updates.
